7问题与风险清单（按优先级）

P0-1 情绪日记管理接口越权（垂直 + 水平越权）建议加功能前修复
对照其他模块（Article / Counseling / GrowthPlan 的管理接口均显式调用 UserContext.isAdmin()），情绪日记的两个管理接口没有任何管理员或归属校验，而 SecurityConfig 对该路径仅要求「登录」。因此任意普通用户登录后即可：① 调 GET /api/emotion-diary/admin/page 分页读取全站所有用户日记正文；② 调 DELETE /api/emotion-diary/admin/{id} 删除任意他人日记。Service 层 adminPage 全表查询、delete 按 id 直删，也未兜底。
修复：在 EmotionDiaryController 的 adminPage / delete 中补 requireAdmin()（与其他 Controller 一致），或上移为统一注解鉴权。改动量极小。
P1-2 AI 知识库与后台文章库「双源未打通」影响 RAG 效果
AI 检索（@Tool MCP 工具 + buildKnowledgeContext）读取的是 classpath 静态文件 resources/knowledge-base/articles.json（实际仅 4 篇：基础认知/睡眠健康/亲子沟通/职场减压）；而后台「知识文章管理」CRUD 的是 MySQL knowledge_article 表。管理员新发布的文章不会进入 AI 检索，前台也并存两套知识库接口（/api/knowledge/** 读 JSON、/api/knowledge/article/** 读库）。这与 README「实时检索知识库、优先引用已发布文章」的描述存在落差。
建议：让 KnowledgeBaseService 改为从 MySQL 已发布文章检索（启动加载 + 发布/下线时刷新），或明确「静态库为演示、DB 库为业务」的定位并在文档说明，逐步收敛为一套。
P1-3 数据分析接口缺管理员校验 中低风险
/api/data-analytics/overview 与 campus-report 只需登录即可访问。overview 返回全站总用户数、活跃数、平均情绪分、趋势等运营指标（不含个人原文，敏感度有限）；campus-report 本就是匿名聚合。建议仍收敛为管理员，避免普通用户看到全站运营口径。
P1-4 V1 已实现的部分安全 / 合规 / 增强能力在 V2 重构后缺失 能力回退
对照 docs/技术方案.md、旧看板与 v1 分支，下列 V1 能力在当前 main 的表与接口中已不存在：首次同意门(user_consent)、三重风险识别与风险事件(risk_event)、危机资源(crisis_resource)、对话帮助度反馈(chat_feedback)、审计日志(audit_log)、文章收藏(article_favorite)、自助练习库(exercise*)、提示词/模型/规则版本化(system_config_version)、用户侧日记自查/编辑/删除/趋势、个人数据导出；SSE 也仅有 message/done/error，缺少技术方案要求的 risk/blocked 结构化安全事件。
这是 V2「重写而非迁移」的结果，不影响 V2 已声明功能，但涉及心理健康产品的安全合规底座（风险识别、危机卡、审计）建议评估是否补回。
P2-5 进度 / 技术文档滞后于代码 文档
docs/实施进度看板.html 仍标注 P2「未开始」、标题为 V1 MVP；docs/技术方案.md 为 V1 版本（仍写 GET stream、硅基流动、Redis，与现状 POST stream、DeepSeek、无 Redis 不符）。本报告即用于校准现状，后续可据此更新看板。

8添加新功能前的就绪评估与建议

① 修 P0-1 越权（约 10 行）→ ② 决定知识库是否并轨→ ③ 新功能按现有分层扩展→ ④ 补最小接口测试

为什么现在可以加功能

  • 前后端均可一次构建通过，分层（controller / service / mapper / entity / dto / config）清晰，新增模块有 P2 三个完整范例可直接仿照。
  • 统一 Result 返回体、全局异常、JWT、UserContext、MyBatis-Plus 分页等基础设施齐备，新增接口成本低。
  • 数据表脚本集中在 schema.sql、种子数据由 DataInitializer 启动写入，新增表 / 种子的路径明确。

新功能落地建议遵循的约定（保持与现有代码一致）

  • 后端：Controller 只做参数与权限，业务进 Service；管理端接口务必显式 UserContext.isAdmin()；用户资源从 JWT 取 userId 并校验归属，不信任前端传参。
  • DTO 分 command / response；入参加 @Valid；返回统一 Result<T>；异常抛 BusinessException 由全局处理器兜底。
  • 前端：用户端 API 放 api/frontend.js、管理端放 api/admin.js；页面按 views 现有布局与路由守卫规则接入。
  • 每完成一个功能：更新对应 README / 文档，并按仓库约定提交 Git commit、同步远程。
