## 1. 方案目标

本技术方案用于指导 Codex-AI 心理健康助手 MVP 的前后端实现、接口补齐、安全风控、数据存储和上线验收。系统面向 18 岁及以上大学生，提供 AI 心理支持、情绪日记、知识库和后台管理能力，但不提供诊断、治疗、用药建议或紧急救援服务。

MVP 技术落地目标：

1. 复用现有前后端分离架构和已有接口能力，降低重建成本。
2. 补齐首次同意、敏感信息授权、个人日记管理、风险事件、对话反馈和审计日志等 P0 缺口。
3. 将高风险识别和危机求助卡做成系统级能力，而不是依赖模型自然语言回复。
4. 确保普通用户只能访问自己的会话、日记和数据导出，管理端默认只查看聚合与脱敏数据。
5. 为后续 P1/P2 的文章推荐、练习库、模型版本化和学校转介能力预留扩展点。

## 3. 总体架构

### 3.1 架构分层

```text
用户浏览器
  -> Vue/Vite 前端应用
    -> API Client / SSE Client / 权限路由 / 风险卡组件
      -> Spring Boot REST API
        -> 认证授权层 Spring Security + JWT
        -> 业务服务层
          -> 用户与同意服务
          -> 心理对话服务
          -> 风险检测服务
          -> 情绪日记服务
          -> 知识库服务
          -> 数据分析服务
          -> 审计日志服务
        -> MyBatis Plus Mapper
          -> MySQL
        -> Redis
        -> 文件存储
        -> Spring AI / 硅基流动模型服务
```

### 3.2 核心设计原则

1. **前端强制安全组件**：风险命中后由接口返回结构化风险等级和行动类型，前端根据字段展示危机卡，不能只依赖 AI 文案中是否提到热线。
2. **后端做最终权限边界**：学生端所有用户数据查询、删除、导出均从 JWT 中解析 `userId`，不信任前端传入的用户 ID。
3. **敏感数据最小化**：风险事件、后台概览、运营报表默认使用脱敏摘要和聚合指标，完整对话内容仅更高权限可访问并写审计日志。
4. **提示词与规则可追溯**：AI 回复、风险识别、危机卡文案、模型版本和规则版本必须写入消息或事件记录。
5. **接口兼容优先**：已有接口保持兼容；新增接口采用同一 `Result<T>` 响应结构和现有错误码体系。

## 4. 前端技术方案

### 4.1 页面与路由

| `/register` | 注册 | 未登录可访问 |
| `/onboarding/consent` | 首次告知与同意 | 登录后未完成同意时强制进入 |
| `/` | 首页 | 登录且完成同意 |
| `/chat` | AI 倾诉对话 | 登录且完成同意 |
| `/chat/:sessionId` | 会话详情 | 仅本人 |
| `/diary` | 情绪日记首页 | 仅本人 |
| `/diary/new` | 新建日记 | 仅本人 |
| `/diary/:id` | 日记详情/编辑 | 仅本人 |
| `/library` | 知识库列表 | 登录后 |
| `/library/:id` | 知识库详情 | 登录后 |
| `/profile/privacy` | 隐私与数据管理 | 仅本人 |
| `/admin` | 后台概览 | 管理员 |
| `/admin/articles` | 文章管理 | 管理员 |
| `/admin/risk-events` | 风险事件中心 | 安全/运营管理员 |
| `/admin/audit-logs` | 审计日志 | 安全管理员 |

前端路由守卫逻辑：

1. 无 token 访问受保护页面时跳转登录。
2. token 存在但未完成同意时，只允许访问同意页、退出和隐私政策。
3. 普通用户访问 `/admin/**` 时显示无权限页面。
4. 接口返回 `401`、`A0230`、`A0301` 时清理本地登录态并引导重新登录。

### 4.2 状态管理

建议拆分以下状态模块：

| 模块 | 主要状态 |
| --- | --- |
| `authStore` | token、用户信息、角色、登录状态 |
| `consentStore` | 年龄确认、隐私政策版本、敏感信息同意版本、完成状态 |
| `chatStore` | 当前会话、会话列表、消息列表、SSE 状态、风险状态 |
| `diaryStore` | 日记列表、当前日记、趋势数据 |
| `knowledgeStore` | 分类树、文章分页、文章详情、推荐文章 |
| `adminStore` | 概览指标、风险事件、文章审核状态 |

token 存储建议优先使用安全 Cookie；若现阶段继续使用 `localStorage`，需避免写入敏感原文，并在退出、过期和账号注销后及时清理。

### 4.3 AI 流式对话

流式对话使用现有 `GET /psychological-chat/stream`。由于 SSE GET 不适合传输过长文本和复杂上下文，MVP 建议升级为以下二阶段流程：

1. `POST /psychological-chat/messages`：提交用户消息，后端完成权限校验、同意校验、输入风险检测和用户消息落库，返回 `messageId`、`riskLevel`、`actionType`。
2. `GET /psychological-chat/stream?sessionId={sessionId}&messageId={messageId}`：基于已落库消息生成 AI 流式回复。

若短期保持现有单一 stream 接口，也必须在响应流首段返回结构化事件：

```text
event: risk
data: {"riskLevel":3,"actionType":"SHOW_CRISIS_CARD","riskEventId":10001}

event: delta
data: {"content":"听起来你现在承受得很重。"}

event: done
data: {"assistantMessageId":20001}
```

前端处理要求：

1. 发送中禁用输入框，但允许用户停止生成。
2. 网络中断时展示重试入口，重试时复用 `messageId`，避免重复写入用户消息。
3. 收到 `riskLevel >= 3` 或 `actionType = SHOW_CRISIS_CARD` 时，置顶展示危机卡并固定在当前会话顶部。
4. 高风险状态下隐藏普通提示词 chips，优先展示 `120`、`110`、`12356` 和校内资源。
5. AI 回复内容按纯文本渲染；如未来支持 Markdown，需要进行 HTML 清理和 XSS 过滤。

### 4.4 情绪日记与趋势

学生端情绪日记以低负担为原则，必填项只保留：

1. 主情绪。
2. 总体状态分 `1-10`。

可选项包括触发事件、想法、身体反应、睡眠、精力、备注。趋势页使用 ECharts 展示 7 天和 30 天状态分变化，并显示记录数量。数据不足 3 条时显示空状态，不输出趋势判断。

### 4.5 知识库富文本安全

知识库文章由管理端编辑，学生端只展示已发布文章。前端渲染富文本时需要：

1. 使用白名单清理 HTML 标签和属性。
2. 禁止 `<script>`、事件属性、`javascript:` 链接和未知 iframe。
3. 图片统一走文件服务域名或可信 CDN。
4. 文章推荐只来自后端已审核文章列表，不能由模型生成虚构文章。

### 5.2 认证与授权

沿用 Spring Security + JWT。JWT 中至少包含：

| 字段 | 说明 |
| --- | --- |
| `userId` | 用户 ID |
| `username` | 用户名 |
| `userType` | 1 普通用户，2 管理员 |
| `status` | 0 禁用，1 正常 |
| `iat` / `exp` | 签发与过期时间 |

后端权限规则：

1. `/user/login`、`/user/add` 允许匿名访问。
2. `/consents/**`、`/user/privacy/**` 登录后访问。
3. `/psychological-chat/**`、`/emotion-diary/**` 必须登录且账号正常。
4. `/admin/**`、文章写接口、风险事件查询、审计日志查询必须管理员权限。
5. 对会话、消息、日记等用户资源，服务层必须校验资源归属。

建议 `GET /psychological-chat/stream` 返回以下事件类型：

| 事件 | 说明 |
| --- | --- |
| `risk` | 风险检测结果，必须在普通文本前尽早返回 |
| `delta` | AI 回复增量文本 |
| `blocked` | 高风险或合规原因导致普通回复中断 |
| `done` | 回复完成，返回助手消息 ID 和模型版本 |
| `error` | 业务或系统错误 |

`risk` 事件数据：

```json
{
  "riskLevel": 3,
```

## 7. AI 与风险控制方案

### 7.1 AI 调用流程

```text
用户输入
  -> 登录、同意、资源归属校验
  -> 输入规则检测
  -> 输入模型分类
  -> 写入用户消息
  -> 高风险分支判断
    -> 危机场景：创建风险事件，返回危机卡事件，使用危机提示词生成极短回复或阻断普通回复
    -> 普通场景：调用心理支持提示词生成回复
  -> 输出安全审核
  -> 写入 AI 消息
  -> 返回 done 事件
```

### 7.2 风险等级

| 等级 | 名称 | 判断示例 | 系统动作 |
| --- | --- | --- | --- |
| 0 | 正常 | 普通压力、轻度情绪表达 | 正常回复 |
| 1 | 关注 | 持续低落、明显无助但无伤害意图 | 温和建议线下支持，可推荐知识内容 |
| 2 | 预警 | 模糊自伤表达、严重失眠、情绪失控 | 展示求助提示，记录风险事件 |
| 3 | 危机 | 自杀计划、正在自伤、伤害他人、立即危险 | 展示危机卡，阻断普通建议，鼓励立即联系现实支持 |

### 7.3 风险检测实现

MVP 使用“规则 + 模型分类 + 输出审核”的组合：

1. **规则检测**：维护高优先级关键词、意图短语和正则表达式，例如自杀、自伤、伤人、立即危险相关表达。
2. **模型分类**：用低温度分类提示词输出结构化 JSON，只允许风险等级、风险类型、置信度和简短理由。
3. **输出审核**：检查 AI 回复是否包含诊断、用药、治疗承诺、保密承诺、虚假人工介入等禁止表达。
4. **人工抽检**：安全管理员定期抽检脱敏样本，更新风险词库和测试集。

### 7.4 提示词治理

现有心理疏导系统提示词需要按产品边界调整：

1. 不使用“专业心理医生”“治疗”“诊断”等会造成角色误解的表达。
2. 明确 AI 是心理支持助手，不替代专业诊疗和紧急救援。
3. 正常回复采用“理解感受 -> 澄清处境 -> 一个小行动 -> 必要时线下支持”的结构。
4. 危机场景使用独立提示词，只输出简短稳定的安全引导。
5. 提示词版本、模型名和供应商写入 `consultation_message.ai_model` 或扩展字段，并在风险事件中记录。

## 8. 数据安全与隐私

### 8.1 敏感数据范围

以下数据按敏感个人信息处理：

1. 心理对话内容。
2. 情绪日记、情绪评分、触发事件、身体反应。
3. 风险事件、风险类型和危机处置记录。
4. 数据导出、账号删除申请。

### 8.2 存储与日志

1. MySQL 存储业务数据，敏感字段建议在应用层加密或使用数据库透明加密。
2. Redis 不缓存完整私密对话；如缓存 SSE 状态，只保留短期 messageId、sessionId 和生成状态。
3. 应用日志禁止输出明文密码、JWT、完整对话、完整日记和模型 API Key。
4. 文件上传限制类型、大小和文件名，进行随机重命名，避免路径穿越。
5. 后台导出必须异步生成、有时效下载地址，并记录审计日志。

### 8.3 权限与审计

管理员权限 MVP 可先沿用 `userType=2`，但服务层应预留角色拆分：

| 角色 | 权限 |
| --- | --- |
| 内容管理员 | 文章、分类、封面和发布状态 |
| 运营管理员 | 聚合数据、脱敏反馈、脱敏风险趋势 |
| 安全管理员 | 风险事件、危机资源、规则版本、提示词版本和审计日志 |

以下操作必须写审计日志：

1. 查看风险事件详情。
2. 导出任何包含用户数据的报表。
3. 修改文章发布状态。
4. 修改危机资源、风险规则、提示词或模型配置。
5. 处理账号删除申请。

## 9. 后端落地细节

### 9.1 DTO 与校验

新增接口沿用现有 DTO 分层：

```text
DTO/command  创建或更新请求
DTO/query    分页和筛选查询
DTO/response 前端响应
```

所有请求使用 Spring Validation：

1. 文本长度限制：单条对话建议 2000 字以内，日记事件建议 1000 字以内，反馈建议 500 字以内。
2. 枚举字段必须使用白名单校验。
3. 分页参数限制最大 `pageSize`，避免后台接口被大分页拖垮。
4. 管理端筛选时间范围建议最大 180 天。

### 9.2 事务边界

1. 发送用户消息：会话归属校验、风险检测结果、用户消息落库和风险事件创建应在同一事务内完成。
2. AI 回复落库：生成完成后单独事务保存助手消息；失败时保留用户消息和失败状态，前端允许重试。
3. 日记更新和删除：必须校验本人归属后事务执行。
4. 账号删除：采用申请状态流转，实际清理异步执行，并保留法律或安全所需的最小审计记录。

### 9.3 异常与响应

沿用现有 `Result<T>` 和 `ResultCode`。建议新增业务错误码：

| code | 含义 |
| --- | --- |
| `CONSENT_REQUIRED` | 未完成必要同意 |
| `AGE_NOT_SUPPORTED` | 未确认已满 18 岁 |
| `RESOURCE_FORBIDDEN` | 无权访问该资源 |
| `RISK_RESPONSE_BLOCKED` | 风险场景阻断普通回复 |
| `DATA_DELETION_PENDING` | 账号删除处理中 |
| `AI_PROVIDER_ERROR` | 模型服务异常 |

## 10. 管理后台方案

### 10.1 数据概览

基于 `GET /data-analytics/overview` 扩展或新增聚合字段：

1. 新增用户数、活跃用户数。
2. 对话会话数、参与用户数。
3. 日记记录数、日记用户数。
4. 对话帮助度正向率。
5. 风险事件数量、待复核数量、危机卡展示成功率。
6. 知识库文章阅读量、发布文章数。

概览页面只显示聚合数据，不展示对话或日记原文。

### 10.2 文章管理

文章状态建议：

| 状态 | 说明 |
| --- | --- |
| `DRAFT` | 草稿 |
| `PENDING_REVIEW` | 待审核 |
| `PUBLISHED` | 已发布 |
| `OFFLINE` | 已下线 |

学生端文章列表只返回 `PUBLISHED`。管理端发布、下线、删除和封面上传需要写审计日志。

### 10.3 风险事件中心

默认列表字段：

1. 时间。
2. 风险等级。
3. 风险类型。
4. 脱敏摘要。
5. 规则版本。
6. 模型版本。
7. 危机卡是否展示。
8. 处理状态。

完整内容查看应二次权限校验并写审计日志。若运营团队没有人工及时介入能力，状态只能表示系统处理和人工复核，不能在页面或 AI 文案里承诺“已通知老师”。

## 11. 测试方案

### 11.1 前端测试

1. 路由守卫：未登录、未同意、普通用户、管理员四类状态。

5. 管理端敏感操作写入审计日志。
6. 文件上传拦截非法类型、超限大小和异常文件名。

### 11.3 安全回归测试集

上线前至少覆盖：

1. 自伤自杀明确表达。
2. 模糊轻生表达。
3. 伤害他人表达。

5. 越狱诱导模型扮演医生。
6. 要求 AI 保密、不告诉任何人。
7. 知识库富文本 XSS。
8. 横向越权访问他人会话、日记和风险事件。

## 14. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 高风险表达漏判 | 用户安全风险 | 规则、模型分类、输出审核和人工抽检组合；上线前维护安全测试集 |
| AI 回复越界 | 合规和安全风险 | 提示词约束、输出审核、危机场景独立提示词、敏感回复拦截 |
| 后台权限过宽 | 隐私泄露 | 角色拆分、默认脱敏、二次权限校验、审计日志 |
| SSE 重试重复写消息 | 历史记录混乱 | 用户消息先落库并返回 `messageId`，重试复用 `messageId` |
| 情绪评分语义混乱 | 用户误解趋势 | 学生端统一为“总体状态 1-10”，后台风险分使用“压力风险”命名 |
| 第三方模型数据处理不清 | 合规风险 | 上线前完成供应商、数据地域、日志保留和备案信息评审 |

## 15. 结论

当前技术基础已能支撑 Codex-AI 心理健康助手 MVP 的主体功能，但上线前必须优先补齐同意管理、用户侧日记 CRUD、风险事件、危机资源、对话反馈、审计日志和流式接口结构化风险返回。技术实现上应把“心理支持边界”和“高风险处置”作为底层能力内建到前后端流程中，确保产品可用、可追溯、可审计，并为后续学校资源接入和专业审核机制留下扩展空间。
